On your computer

Passwords, ports, and why local testing is simpler than the live site.

Two programs, one command

When you run the project locally, two separate programs start. The website is what you see in the browser. The practice probe is a small helper that actually fetches URLs and measures time. A launcher script starts both so you do not have to manage them manually.

What starts when you run dev:local

Settings (environment variables)

Programs read secret settings from a local config file (not committed to git). You only need to care about a couple of names:

PROBE_SECRET — the shared password

Think of this as a handshake between the website and the probes. The website says “I am allowed to run tests” by sending a password. Probes ignore strangers without the password. On your laptop you pick any non-empty password and put it in the config file. In production the same password must be configured on the hosting platform and on every probe.

Unit tests set this password themselves when they simulate probe calls — you do not need a local config file just to run npm test.

dev:local vs dev:app

dev:local — easiest. Website and practice probe start together. Use this while learning.
dev:app — only the website. Use this if you are changing how things look and do not need live measurements, or if you want to start the probe yourself in a second terminal window.

Your laptop vs the live internet

Locally you have one probe pretending to be a region. On the live site, five probes in different countries run in parallel. Vercel calls all five at once and merges the results — no separate coordinator service.
